# RescueTwin policy platform design proposal

RescueTwin’s next milestone is a local simulator where a developer can run their own search, navigation, or perception policy on one reference robot and compare it with a built-in baseline. The first release should exercise the parts of motion and sensing that change policy outcomes: turning, stopping, getting blocked, losing visibility, missing a frame, and replanning while conditions change. Keep one floor, known localization, and the existing human escort constraints.

## Reference robots

| Field example | Design implication for RescueTwin |
| --- | --- |
| **Quince** is a compact tracked rescue robot adapted for remote inspection and deployed at Fukushima Daiichi. Its articulated tracks addressed terrain well beyond a flat indoor floor. | Use a compact tracked scout as the reference shape and make its footprint, turning, and camera mounting matter from day one. [Tohoku University](https://www.tohoku.ac.jp/en/research/research_highlights/research_highlight_14.html), [Quince deployment team](https://k-nagatani.org/pdf/2012-FSR-Yossy-online.pdf) |
| **PackBot 525** is a commercial remotely operated ground robot tested in a DHS emergency-response assessment that included medical response, spill investigation, and collapse reconnaissance. | Evaluate maneuverability and camera performance together in scenarios with specific tasks. [Teledyne FLIR account of the SAVER assessment](https://defense.flir.com/about/news/packbot-is-top-dog-in-dhs-saver-study/) |
| **Colossus** is a heavier tracked firefighting robot that the Paris Fire Brigade deployed at Notre-Dame. Its equipment includes a water monitor and a video turret with thermal imaging. | Treat suppression as a distinct mission class. Thermal imaging is worth adding once there is a defined sensor model and a test for how it behaves. [Shark Robotics deployment account](https://www.shark-robotics.com/notre-dame-fire-how-technology-helped-preserve-a-global-icon/), [Colossus specifications](https://www.shark-robotics.com/colossus-firefighting-robot/) |
| **Spot** is a sensor-carrying quadruped. At Y-12 it helped responders remotely inspect an unknown chemical spill. | Consider legged mobility when stairs, rough terrain, or climbing become benchmark tasks. [Boston Dynamics robot overview](https://support.bostondynamics.com/s/article/about-the-spot-robot), [Y-12 deployment account](https://www.y12.doe.gov/news/blog/spot) |

These examples span different jobs. The shared starting point for RescueTwin is a ground vehicle that gathers information where a responder has limited visibility or access. The close analogue for the current single-floor benchmark is a compact reconnaissance robot. Survivor escort remains a RescueTwin mission behavior. Use NIST’s response-robot test methods as inspiration for repeatable mobility and sensing fixtures. [DHS emergency-response UGV focus group](https://www.dhs.gov/sites/default/files/2025-05/25_0507_st_ugvfgr_0.pdf), [NIST ground robot tests](https://www.nist.gov/el/intelligent-systems-division-73500/standard-test-methods-response-robots/ground-robot-tests)

## Robot and navigation

- Ship a single RescueTwin-owned, tracked-style skid-steer profile. Model a rectangular footprint, continuous planar pose `(x, y, yaw)`, forward and reverse motion, turns in place, bounded linear and angular speeds, acceleration, and braking. Lateral motion is constrained by the drive model. Record the footprint, camera extrinsics, and motion limits with each run. Derive the initial dimensions from verified doorway clearances and label them as simulator parameters until there is a hardware target.
- Use a reviewed collision layer with floor boundaries, walls, door openings, and simple obstacle geometry. Check the swept footprint during translation and rotation. A clearance check can block motion before contact. An actual simulated contact can stop the robot and report a bumper event. Use conservative collision response for the first release. Track forces, suspension, slip calibration, and movable-object dynamics can wait.
- Keep the occupancy grid and A* for global routing and hazard costs. Execute routes with a continuous, footprint-aware local controller and replan when the route becomes blocked. Add an orientation-aware planner only if the turning fixtures reveal a material failure of grid A* with local tracking. A robot can need more freedom in how it moves even when its global planner still uses a raster map. Nav2’s Regulated Pure Pursuit is a reference for curvature-based slowing and predictive footprint checks. [Nav2 controller documentation](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/controller_plugins/configuring_regulated_pp/)

Use a lightweight planar simulation for the first milestone. The integration points are pose and motion, collision geometry, sensor output, and simulation time. Gazebo is the first backend to evaluate when a ROS 2 integration or dynamic contacts become a requirement. It already offers drive systems and contact, camera, and range sensors. MuJoCo becomes relevant when contact dynamics or actuator-level experiments change the research question. Isaac Sim becomes relevant when RTX sensor rendering or large synthetic datasets justify its workstation requirements and scene conversion. Compare an alternative backend on the same doorway and visibility fixtures before adopting it. [Gazebo Sim](https://gazebosim.org/libs/sim/), [MuJoCo contact computation](https://mujoco.readthedocs.io/en/stable/computation.html), [Isaac Sim overview](https://docs.isaacsim.omniverse.nvidia.com/latest/overview/overview.html), [Isaac Sim requirements](https://docs.isaacsim.omniverse.nvidia.com/latest/installation/requirements.html)

## Policy interface and timing

Run the policy in a separate, developer-started process and give it a versioned, run-scoped API. Ship a small Python example using that API. Consider an SDK or ROS 2 bridge once the command and observation contracts have settled. Keep v1 local and run user code on the developer’s own machine. Policy clients can read only their run’s robot observations and submit commands. Scenario editing, complete hazard and survivor state, recordings with evaluation truth, and renderer administration belong on the operator side. Require separate operator access, since the existing localhost operator API and stream expose simulator state.

- **Mission control.** Start with `navigate_to_pose`, `scan`, `stop`, and the existing validated escort workflow. The built-in path follower handles motion for mission policies. Add a separate bounded velocity mode `(v, ω)` in the same release so navigation developers can replace the local controller. One controller owns motion at a time. Command validation, collision checks, and the mandatory escort interlock apply in both modes.
- **Observations.** Publish pose and twist under the known-localization assumption, static map, observed hazard samples, contact status, mission feedback, and timestamped sensor frames. Expose RGB and degraded depth so developers can test their own perception. Existing YOLO detections can be optional derived observations with provenance. Keep simulator entities out of policy observations and report invalid or stale measurements explicitly. Local smoke and temperature probes should sample at their modeled locations. A computed distance to a known ignition point should remain a development diagnostic.
- **Command feedback.** Include the run, observation sequence, command ID, status, and reason for blocks or overrides. Set a validity window for velocity commands and bring the robot to a controlled stop when the command expires or the policy disconnects during a paced run. Record requested and applied commands so policy decisions and simulator interventions can be inspected independently.
- **Run modes.** Use fixed-step lockstep for seeded regression and replay, with explicit advancement and a bounded host-side wait. Add a paced mode where motion and hazards advance independently of policy and camera latency. Measure policy deadline misses and sensor age in that mode. A stale frame should never be silently reused as a fresh one. Run a dedicated local offscreen sensor worker and keep the workbench optional for batch runs. Measure renderer throughput separately from control timing.

The current prototype sequences RGB-D through a browser frame request and can hold the simulation tick for the response. The robot observation API also returns a different shape from the internal `rescuetwin.observation/1` envelope. Use the internal contract as a starting point. Define a public allowlist for observations and safe map metadata, and test it against hidden world state and private scene provenance. [Simulation tick](../rescuetwin/core.py), [Observation contracts](../rescuetwin/contracts.py), [Local API](../rescuetwin/api.py), [Camera pass](../frontend/src/main.ts)

## Fire and smoke perception

Treat visible smoke and flame as part of the sensor model. The prototype applies camera-local RGB fog and renders geometric depth in a separate pass. For the next version, let a shared, seeded, coarse 3D hazard field describe smoke density, temperature, and flame regions. Sample local hazard instruments and render from the same time-indexed field. Use a simple height-dependent smoke model with compartments and door openings as a first approximation. Preserve existing 2D hazard and belief maps behind a documented projection during the transition.

Integrate optical attenuation along each camera ray to the visible surface so the robot can see a smoke layer ahead while it is still in clear air. Render flames as emissive regions at their modeled locations, with low-light contrast and glare represented in the camera output. Model depth as its own sensor, including configurable noise and invalid returns in obscured regions. Keep geometric depth for evaluator checks. Add range sensing or simulated thermal as distinct modalities once a policy needs them, with explicit assumptions about occlusion, noise, and saturation. The desired outcome is a measurable change in detection and navigation as visibility drops. [NIST optical smoke and thermal camera test facility](https://www.nist.gov/publications/bench-scale-test-facility-evaluating-imaging-performance-thermal-imagers-fire-service), [NIST FireLiDAR](https://www.nist.gov/programs-projects/national-fire-research-laboratory-advanced-metrology/firelidar)

Use NIST Fire Dynamics Simulator output offline for reference cases once a synthetic geometry and its fire and ventilation inputs are defined. Compare simple observables such as sightline attenuation and the timing of smoke at different camera heights. Store any precomputed fields as versioned scenario inputs. Keep interactive fire behavior labeled as an approximation and simulated exposure as a benchmark metric. [NIST FDS and Smokeview](https://pages.nist.gov/fds-smv/)

## Scene assets

Build a redistributable synthetic corridor-and-rooms scene with reviewed exit semantics, camera geometry, and collision geometry. Matterport and CoStar remain optional local inputs. Keep render geometry, collision geometry, and hazard compartments as distinct registered layers in one metric frame. This lets a cleaned scan replace the visual layer while preserving an audited doorway or wall in the collision layer.

Future digital-twin work can capture interiors with permission and use 3D Gaussian Splatting for higher-quality camera views. Pair the visual reconstruction with independently reviewed metric geometry for collision, depth evaluation, door semantics, and smoke boundaries. Preview registration and occlusion together before using a new capture for a benchmark. [Original 3D Gaussian Splatting paper](https://repo-sam.inria.fr/fungraph/3d-gaussian-splatting/)

Defer external robot definitions until a second maintained robot profile demonstrates which vehicle capabilities the policy contract needs to describe.

## First milestone and acceptance

1. **Contract and reference runner.** Freeze one public synthetic scene and robot profile. Run a built-in A* baseline and a separate example policy through the same vehicle and safety path. Verify schema compatibility, policy access, command expiry, action logging, and replay.
2. **Continuous mobility.** Add a narrow but passable doorway, a turn where the footprint clips the corner, and a corridor blocked by a static obstacle. Verify braking, reverse, contact reporting, replanning or holding, and escort stops when a follower’s route crosses the existing limits.
3. **Sensor credibility.** Run clear-air, partial-smoke, and blocked-visibility variants with the same scene and placements. Check RGB attenuation versus distance, degraded depth validity, and wall occlusion. Run the sensor worker with the workbench closed and check delayed and missing frames in paced runs.
4. **Comparative evaluation.** Freeze scene, placements, robot, sensor profile, seed, and safety rules. Compare clear versus smoky detection with one policy and compare two policies under identical conditions. Report time to first credible detection, confirmed detections and false positives, contacts and stops, evacuation or handoff, simulated exposure, and timing misses. Check repeatability on the same backend and configuration. Use tolerance-based comparisons for GPU image outputs.

Release when a developer can run the example policy and baseline on the same public scenario with the workbench closed, inspect the recorded decisions and interventions, and see a repeatable drop in perception quality as the smoke thickens. Use that result to decide whether the next investment is better sensors, dynamics, or scene capture.
